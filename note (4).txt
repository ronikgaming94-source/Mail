MAIL.TM API — MANDATORY IMPLEMENTATION

Use the official Mail.tm API.

Base API:

https://api.mail.tm

No Mail.tm API key is required.

The implementation must follow this sequence:

STEP 1:
GET /domains

Retrieve active Mail.tm domains.

Only use domains where isActive=true.

Do NOT hardcode a Mail.tm domain.

Cache the available domain list for a reasonable period so the bot does not repeatedly request /domains.

STEP 2:
POST /accounts

Create a real Mail.tm account.

Request:

{
"address": "randomusername@domain",
"password": "secure_random_password"
}

Generate cryptographically random mailbox usernames.

Do not generate predictable usernames.

STEP 3:
POST /token

Request:

{
"address": "mailbox_address",
"password": "mailbox_password"
}

Store the returned Mail.tm account ID and token securely in PostgreSQL.

STEP 4:
Use:

Authorization: Bearer TOKEN

for authenticated Mail.tm requests.

MAILBOX CREATION BUSINESS LOGIC

USER CLICKS:

Before creating:

1. Check user exists.
2. Check user is not banned.
3. Check maintenance mode.
4. Check force subscription.
5. Check user has at least 1 credit.
6. Check Mail.tm API availability.
7. Retrieve a valid active domain if needed.

Then create the Mail.tm account.

CRITICAL CREDIT RULE:

1 successful Mail.tm account = 1 credit.

DO NOT deduct credit before successful creation.

Correct sequence:

START TRANSACTION

Lock user credit row.

Check balance >= 1.

Call Mail.tm account creation.

Call Mail.tm token creation.

Verify successful account/token.

Create local Mailbox database record.

Deduct exactly 1 credit.

Create CreditTransaction.

COMMIT.

If ANY Mail.tm operation fails:

ROLLBACK.

DO NOT deduct the credit.

DO NOT create a broken local mailbox.

This must be race-condition safe.

If user presses Create New Mail multiple times rapidly, only valid successful mailbox creations should consume credits.

INCOMING EMAILS — REAL-TIME

THIS IS A CRITICAL REQUIREMENT.

Do NOT make users manually open Inbox.

Use Mail.tm's real-time event system.

Mail.tm provides Mercure Server-Sent Events.

Mercure hub:

https://mercure.mail.tm/.well-known/mercure

Topic:

/accounts/{account_id}

Authenticate using:

Authorization: Bearer MAILBOX_TOKEN

For every active Mail.tm mailbox, maintain a real-time listener.

When a new account event indicates new mail:

1. Identify the mailbox/account.
2. Find the corresponding local user.
3. Fetch the actual message using:

GET /messages/{message_id}

or the appropriate Mail.tm message endpoint.

4. Parse sender.
5. Parse recipient.
6. Parse subject.
7. Parse text.
8. Safely sanitize HTML.
9. Save the message in PostgreSQL.
10. Prevent duplicate processing.
11. Send Telegram notification immediately.

Do NOT depend on users pressing Refresh.

==================================================
REAL-TIME LISTENER ARCHITECTURE

Create a dedicated background service:

MailEventManager

Responsibilities:

- Start listener for every active mailbox.
- Maintain SSE/Mercure connections.
- Reconnect automatically after disconnect.
- Handle expired/invalid tokens gracefully.
- Refresh/re-authenticate mailbox token when necessary.
- Backoff after repeated failures.
- Stop listeners when mailbox is deleted.
- Start listeners for existing mailboxes after bot restart.

Do NOT create one uncontrolled infinite task per request.

Track active listeners centrally.

Use asyncio tasks safely.

When the application restarts:

1. Load all active mailboxes from PostgreSQL.
2. Validate their status.
3. Start their real-time listeners again.

SECURITY OF MAIL.TM CREDENTIALS

Every Mail.tm account requires a password and token.

Never send these to Telegram users.

Do not put them in logs.

Do not expose them through admin UI.

Prefer encrypted storage using an application encryption key.

Create:

ENCRYPTION_KEY=

environment variable.

If encryption implementation is too complex for the first version, isolate credential storage behind a service abstraction so it can be upgraded safely.

==================================================
RATE LIMITING

Mail.tm has an API rate limit.

The current general Mail.tm API quota is 8 queries per second per IP.

Implement a global async rate limiter for Mail.tm requests.

Do not fire unlimited concurrent API requests.

Add exponential backoff for 429 responses.

For 429:

Wait and retry safely.

Do not deduct user credits on failed creation.
